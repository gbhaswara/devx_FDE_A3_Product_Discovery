# How I built this with AI tools

I used **OpenCode** with the **9router** endpoint (deepseek-v4.1-flash) as the primary coding agent, backed by a spec-driven workflow I built myself (**openspec**) that kept proposal, capability specs, design decisions and task lists in one place. The model drafted the site analysis, the eleven capability specs and most of the code across 86 commits; I reviewed and corrected every draft, and the scope decisions are mine. The model earned its place by finding defects: live-model evaluation exposed a clarification branch that unit tests had made unreachable, plus a colour ambiguity only the model's phrasing triggered. I kept the pricing arithmetic, the evaluation design and the five-axis definitions (interpretation, retrieval, match, pricing, reply) under human ownership. At runtime the model interprets free-text requests only — it never prices, never selects a product, and never writes a total; every figure comes from deterministic code. I also used **Context7** for library documentation, and **MCP tools** (local-memory, hindsight) for persistent memory across sessions, recording decisions, facts, mistakes and patterns after every phase boundary. The build progressed in five archived openspec changes: Tier 1 (0.5.0), three Tier 2 extras, conversation memory, and the gap-closure that fixed the first brief-audit findings. A final section-by-section review against the brief's five "what we look for" criteria then found eight more defects (`BUG.md` A23–A30) — a restock date copied onto in-stock rows, a per-ream budget compared as if per pack, a duplicated SKU losing its volume tier, two products merged into one impossible request, and replies that withheld the free-delivery threshold and a cheaper larger quantity. Each was reproduced first, registered, fixed with a failing test, and closed only after the suite, the evaluation set and the refresh harness all passed.
